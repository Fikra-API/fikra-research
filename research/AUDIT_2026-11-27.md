# Security and correctness audit, 2026-11-27

Reason: the instructions that drove Phase 1 came from an agent later reported by
the owner as having poisoned other code. The research repository had to be
checked before any of its numbers were trusted.

Scope: `Fikra-API/fikra-research` at `b013a64`. 20 commits, 17 authored by
Fikra Code, 3 by "Lacesse".

## 1. Authorship

Every kernel file (`model_spec.py`, `nvfp4.py`, `gemv_triton.py`, `routing.py`,
`decode_budget.py`, `kernel_spec.py`, `tensor_reader.py`, `gemv_torch.py`)
arrived in `db81603`, authored "Lacesse". That is the commit that had to be
scrutinised, not the ones that followed.

## 2. Exfiltration

Checked for network calls, subprocess, exec/eval, encoded literals and
environment reads in every non-test module.

- The only network code is `tensor_reader.py`, which range-reads a URL it is
  given. No hardcoded host, no fallback endpoint, no telemetry.
- No `subprocess`, no `os.system`, no `eval`, no `exec`, no `pickle`, no base64.
- No access to environment variables outside `benchmark.py`'s
  `FIKRA_BENCHMARK_DIR`, which is a documented local path setting.
- No secrets, keys or tokens in any file.

**Verdict: no exfiltration path.**

## 4. Format constants

- E2M1 magnitude table checked against the published values
  (0, 0.5, 1, 1.5, 2, 3, 4, 6 and negatives): exact.
- E4M3 decode checked at 0x38, 0x3C, 0x40, 0x00, 0xB8: exact.
- Roofline arithmetic recomputed by hand: 320e9 / 4.654e9 = 68.8 tok/s, matching
  the module.

**Verdict: constants and formulas correct.**

## 5. Defect found and fixed

`nvfp4.quantize_e2m1` claimed "ties to even index" but used `searchsorted` plus
a strict `<`, so all seven exact midpoints (0.25, 0.75, 1.25, 1.75, 2.5, 3.5,
5.0) rounded UP instead of down. Measured: 7 of 701 sampled magnitudes wrong,
1.0%.

Impact: **test-only**. The function has no production caller; the kernels
dequantise and never quantise. No measured number was affected. Fixed, with two
contract tests so it cannot silently regress.

This looks like an ordinary off-by-one, not sabotage: it is the kind of bug you
get from writing `searchsorted` and a strict comparison without testing the
midpoints, and it made the helper *less* accurate rather than quietly
favouring any result.

## 6. One false alarm, recorded for honesty

I initially reported the routing heatmap as off by one, returning 7 experts
where I expected 8 for 80% coverage. It is correct: 7 of 8 equally-used experts
already cover 87.5%, so 7 is the right answer. My expectation was wrong, not the
code. Written down so the audit is not read as finding two defects.

## 7. What is not verified by this audit

- The Strata measurements were produced by a third-party engine on Kaggle. The
  numbers are quoted from its own JSON, but the engine itself is outside our
  control; only the harness that read it is ours.
- The Kaggle kernels that produced the timing results are ephemeral and their
  images are not pinned. Re-running the same kernel tomorrow may not reproduce
  the same numbers, which is why the throttling finding matters.
- No audit of the other repositories, only this one.

## Bottom line

No exfiltration, no fabricated constants, no poisoned arithmetic. One genuine
off-by-one in a test helper, fixed. The measured results stand as measured,
subject to the throttling caveat already recorded in
`results/releases/2026-11-27_kernel1_harness_pass3.json`.
